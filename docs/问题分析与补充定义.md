## 一、测试点标识规则修正

### 1.1 金标准实际规则（从 Excel 确认）

从《区域影像测试用例.xls》提取的实际格式：

| 系统 | 父目录(主模块) | 子系统(子模块) | 测试点标识 | 用例编号示例 |
|------|---------------|---------------|-----------|-------------|
| 区域影像系统(QYYX) | 配置(PZ) | 检查室(JCX) | `QYYX_PZ_JCX` | `QYYX_PZ_JCX_01` ~ `QYYX_PZ_JCX_05` |
| 区域影像系统(QYYX) | 配置(PZ) | 公共知识库(GGZSK) | `QYYX_PZ_GGZSK` | `QYYX_PZ_GGZSK_01` ~ `QYYX_PZ_GGZSK_11` |
| 妇幼信息系统(FYXX) | 门诊主页(MZZY) | 孕妇列表(YFLB) | `FYXX_MZZY_YFLB` | `FYXX_MZZY_YFLB_01` ~ `FYXX_MZZY_YFLB_0N` |

**规则总结**：

```
测试点标识 = 系统中文缩写_父目录中文缩写_子系统中文缩写
用例编号   = 测试点标识_编号递增(2位, 从01开始)
编号维度   = 子系统级别(同一子系统内从01递增, 不同子系统各自从01开始)
```

### 1.2 当前 spec/原型的问题

| # | 位置 | 问题 | 修正 |
|---|------|------|------|
| 1 | 主规格 §5.3 | "拼音+`_NN` 全表唯一" 描述不准确 | 改为"系统缩写_父目录缩写_子系统缩写_编号递增(子系统维度)" |
| 2 | 主规格 §6 | `QYYX_PZ_JCX_01` 示例缺少说明这是"测试点标识+编号" | 补充说明：测试点标识=`QYYX_PZ_JCX`，用例编号=`QYYX_PZ_JCX_01` |
| 3 | 原型 Screen3 R174 | `QYYX_PZ_BG_JCBG_01` 错误(多了PZ) | 应为 `QYYX_BG_JCBG_01`（父目录=报告=BG，不是配置=PZ） |
| 4 | D:\Test `featureMarkerBase` | base 包含 4 段(系统+主模块+子模块+功能点)，应只含 3 段(系统+主模块+子模块) | 移除功能点缩写段，编号按子系统维度递增 |
| 5 | D:\Test `assignFeatureTestPointIds` | 计数器维度是 `base`(含功能点)，应改为 `子系统维度` | counter key 改为 `系统缩写_父目录缩写_子系统缩写` |

### 1.3 正确的生成逻辑

```typescript
// 测试点标识 = 系统缩写_父目录缩写_子系统缩写（3段）
// 用例编号   = 测试点标识_NN（4段，NN 按子系统维度从01递增）

function generateTestPointId(systemName, mainModule, subModule): string {
  return [
    toInitials(systemName),    // QYYX
    toInitials(mainModule),    // PZ
    toInitials(subModule),     // JCX
  ].join('_');
}

function generateCaseNo(testPointId, indexInSubsystem): string {
  return `${testPointId}_${String(indexInSubsystem).padStart(2, '0')}`;
  // QYYX_PZ_JCX_01
}
```

### 1.4 字段映射完整定义

功能点表与测试用例表的字段对应关系：

| 功能点表(九列) | → | 测试用例表(八列/meta) | 说明 |
|---------------|---|---------------------|------|
| 系统名称 | → | meta.系统名称 | 直接映射 |
| 主模块 | → | 测试点标识(第2段) | 缩写后作为 base 组成 |

### 2.2 当前原型的问题

原型 HTML 中 `thead` 写在 `tbody`(meta头) 之后，但 HTML 规范规定 `thead` 总是渲染在所有 `tbody` 之前，导致列头跑到 meta 头上方。

### 2.3 修正方案

**Excel 结构顺序（从上到下）**：

```
① meta 头（可编辑行）：系统名称/测试点标识/测试点/测试人员/委托/开发/时间/规则/预置条件
② 列头行：用例编号 | 测试内容 | 步骤 | 输入及操作说明 | 预期结果 | 初次测试结果 | 回归测试结果 | 测试结论
③ 用例数据行：QYYX_PZ_JCX_01 | 查询 | Step1 | ... | ... | \ | \ | \
④ 软件截图行
```

**HTML 修正**：使用多个 `tbody` 替代 `thead`，或拆分为两个 table。

## 三、子系统工作流设计

### 3.1 问题分析

当前原型以单系统为设计基准，工作台显示"项目 > 系统 > 子系统"三级树，但探索/功能点/用例/执行各阶段缺乏明确的"当前子系统"上下文切换机制。

核心矛盾：
- 门户系统下有多个子系统，每个子系统需要独立走完 探索→功能点→用例→执行 全流程
- 如果在工作台切换子系统，后续每个阶段都要跟着切换，用户容易迷失
- 如果不切换，各阶段数据混淆

### 3.2 设计方案：子系统上下文 + 快速切换

**方案核心**：每个子系统拥有独立的流水线状态，顶部上下文栏始终显示当前操作的子系统，支持一键切换。

```
顶部上下文栏（始终可见）：
项目：延安市医疗集团 > 系统：区域影像 > 子系统：[检查室管理 ▾]
                                              ├─ 检查室管理 (探索✓ 功能点✓ 用例✓ 执行⏳)
                                              ├─ 检查项目管理 (探索✓ 功能点⏳)
                                              ├─ 影像归档 (探索⏳)
                                              └─ + 新建子系统
```

**设计要点**：

| 维度 | 设计 |
|------|------|
| 上下文栏 | 顶部始终显示"项目 > 系统 > 子系统"，子系统名可点击展开快速切换菜单 |
| 独立状态 | 每个子系统在每个阶段(探索/功能点/用例/执行/缺陷)有独立数据，互不干扰 |
| 进度标识 | 切换菜单中显示每个子系统的阶段进度(✓/⏳/—)，一眼可知哪个做完了 |
| 阶段导航不变 | 侧栏的"探索→功能点→用例→执行→缺陷"导航不变，点击后展示当前子系统的对应数据 |
| 工作台总览 | 工作台仍显示全局视图(所有子系统的进度统计)，但点击某子系统即切换上下文 |
| 跨子系统操作 | V1 不做跨子系统批量操作(如"为所有子系统生成用例")，V2 考虑 |

### 3.3 子系统与单系统的一致性

子系统登录完成后，后续流程与单系统完全一致：

```
门户登录(一次) → 子系统A: 探索→功能点→用例→执行→缺陷
                → 子系统B: 探索→功能点→用例→执行→缺陷
                → 子系统C: 探索→功能点→用例→执行→缺陷
```

子系统切换不涉及重新登录(门户会话复用)，只切换工作上下文。

### 3.4 人工补录插入位置

当前设计：人工补录只能追加到模块树末尾。

**修正设计**：

```
用户在探索页模块树中：
  ① 右键某个探索项 → 弹出菜单 → "在此上方补录" / "在此下方补录"
  ② 或选中某项后点"人工补充"按钮 → 弹窗选择插入位置(上方/下方/末尾)
  ③ 打开可见浏览器，人工点击未探索页面
  ④ 录制完成后，新节点插入到指定位置（而非末尾）
```

I/O 补充字段：

```typescript

  clickPath: ClickPath[],
  insertPosition: 'above' | 'below' | 'end',
  relativeToNodeId: string | null,  // 相对于哪个节点插入
}
```

## 五、核心数据类型定义

基于 D:\Test 源码分析 + 主规格要求，定义核心数据类型。

### 5.1 ModuleNode（模块树节点）

```typescript
/**
 * 模块树节点 — 探索阶段的输出
 * 对应主规格 §5.2 moduleTree: ModuleNode[]
 */
interface ModuleNode {
  /** 节点唯一 ID（UUID 或路径哈希） */
  id: string;
  /** 显示名称（如"检查室列表"、"关键字查询"） */
  label: string;
  /** 父节点 ID，根节点为 null */
  parentId: string | null;
  /** 所属子系统 ID */
  subsystemId: string;
  /** 节点类型 */
  type: 'system' | 'module' | 'page' | 'action';
  /** 探索状态 */
  status: 'covered' | 'needs_review' | 'unexplored';
  /** 子节点 */
  children: ModuleNode[];
  /** 页面 URL（type=page 时有值） */
  url?: string;
  /** 页面标题（type=page 时有值） */
  pageTitle?: string;
  /** 探索证据 ID（关联到探索快照） */
  evidenceId?: string;
  /** 树深度（根=0） */
  depth: number;
  /** 人工补充标记 */
  manuallyAdded?: boolean;
  /** needs_review 原因 */
  reviewReason?: string;
}

/** 探索阶段输入补充 */
interface ManualSupplement {
  /** 人工点击路径 */
  clickPath: ClickPath[];
  /** 插入位置 */
  insertPosition: 'above' | 'below' | 'end';
  /** 相对于哪个节点插入 */
  relativeToNodeId: string | null;
}

/** 人工点击路径记录 */
interface ClickPath {
  /** 点击序列 */
  steps: ClickStep[];
  /** 归属模块（自动推断或人工选择） */
  inferredModule: string;
  /** 置信度 */
  confidence: number;
}

interface ClickStep {
  /** 点击元素的 CSS selector 或文字描述 */
  selector: string;
  /** 元素可见文字 */
  text: string;
  /** 页面 URL */
  url: string;
  /** 时间戳 */
  timestamp: number;
}
```
