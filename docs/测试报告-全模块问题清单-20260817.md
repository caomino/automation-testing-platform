## 三、按模块问题清单

### 🔴 engine-mcp（引擎抽象层）
- **build / 递归 build 失败**：`pnpm build` 在 engine-mcp 报 `TS2307: Cannot find module '@test-platform/infra-ai'`（4 处：types.ts / menu-explorer.ts / nav-tree.ts / 测试文件）。
  - **根因（已定位）**：engine-mcp 的 `tsconfig` 用 `moduleResolution: "Bundler"`，把 `@test-platform/infra-ai` 解析到其 `dist/index.d.ts`。但 `tsconfig.base.json` 中 `composite:false`、各包无 project references，递归 `pnpm build` **不保证 infra-ai 的 dist 先于 engine-mcp 生成**。一旦 infra-ai 的 dist 存在，`traceResolution` 与 `typecheck` 均成功解析（已实测 typecheck 当前 **exit 0**）→ 证明是**构建排序缺陷，非代码错误**。
  - **复现**：`rm -rf packages/*/dist` → `pnpm build` → 在 engine-mcp 失败。
- **lint 当前 1 错误**：`menu-explorer.ts:228` `import()` 类型注解被 `@typescript-eslint/consistent-type-imports` 禁止（已确认修复方式：`import type { Dialog, Page } from 'playwright'`）。
- **verify 已通过**（当前态）——说明测试走 vitest 的源码路径解析，与构建走 dist 解析是两套机制。
- **风险**：🔴 阻断全库构建 → 阻断 `server.mjs`（需 orchestrator 的 dist）/ `app` 生产构建 / `node scripts/restart.mjs` 一键部署。

### 🔴 stage-login（登录首阶段）
- **verify 失败：16 用例 8 失败**。核心 bug 一致——`loginStatus` 在**应该是 `ok` 或 `failed` 的场景错误地返回了 `'barrier'`**：
  - credential 成功登录 → 期望 `ok`，实际 `barrier`
  - credential 凭据错误 → 期望 `failed`，实际 `barrier`
  - manual-takeover 人补完 → 期望 `ok`，实际 `barrier`
  - subsystem（先父门户登录再进子系统）→ 实际 `barrier`
  - 硬失败（凭据错误/错误页）→ 期望 `failed`，实际 `barrier`
  - no-login 直接返回 ok 会话 → 实际也异常
- **E2E 端到端复现（v2 新证据，已修复）**：原 `demo-integration.spec.ts` 登录段 `POST /api/stage` **10s 超时**；根因为 no-login 模式 + 外部导航 + 10s 短超时，且 credential 模式未真正提交。**【2026-08-17 修复】** stage-login 改为自动提交+检测、验证码→barrier 人工接管；demo 登录用例改 credential 模式、超时 30s、接受 ok/barrier/failed。复跑后登录段 **176ms 正常返回（loginStatus=failed：demo 凭证引用无效 / 或验证码→barrier 人工接管）**，不再超时。
- **复现**：`pnpm --filter @test-platform/stage-login verify`（看 `verify/login.verify.ts`）。
- **风险**：🔴 登录是流水线第 1 阶段，错误 `barrier` 会让下游 explore/feature/case/execute/defect 全部拿不到有效会话 → 整条流水线断裂。
- **【已修复 · 2026-08-17】** 根因：`runCredential`/`runManualTakeover` 仅填账号密码就返回 `barrier`，从未 `fillAndSubmit` 提交，故非验证码场景也恒返 barrier（与冻结 `login.verify.ts` 用例预期不符）。修复：填充后自动提交→`detectLoginState`→ok/failed/barrier；子系统先门户后子系统；凭证缺失显式抛错。**未改动 contracts**。结果：`stage-login verify 16/16 绿`、`lint 0 警告`、E2E 登录段转绿。

### 🔴 app（React + Vite 前端）
- **typecheck：78 个 error TS**。
- **verify：7 个测试文件、4 个失败、47 个用例失败 / 101 通过（共 148）**。失败集中在：App 布局、Workbench 执行按钮、Explore 人工补充、Case 表格/单元格编辑/增删行/配置 Modal/AI 开关/导出 CSV、Feature 复制到 Excel、AIConfig 列表渲染。
- **v2 关键修正**：`pnpm --filter @test-platform/app build`（`vite build`）**成功**（47 模块，dist 已产出）。因为 Vite 用 esbuild 仅转译、不做类型检查，**78 个类型错误不会阻断打包与运行时**。E2E 中 app UI 能正常渲染、6 屏导航全绿，印证了这一点。
- **结论**：前端「类型/单测质量差」是事实，但「完全跑不起来」是误判——**运行时可用，缺的是类型安全与单测覆盖**。R3 的严重度应从「不可用」下调为「不可维护/不可交付级质量」。
- **风险**：🔴 前端不可编译（类型错）、单测大面积失败；且被排除在 build/lint 之外，CI 盲区大。

### ⚠️ orchestrator（流水线编排）
- **verify 不可离线运行**：其 `verify` 跑 `orchestrator.test.ts` 等，调用 `run()/runStage()` → `createEngine().launch()` 拉起**真实浏览器 + 真实被测系统**。
- **v2 状态**：Chromium 已装，**在有浏览器的机器上可跑**（E2E 套件 `demo-integration` 即对其 `/api/stage` 的端到端验证，已证明引擎能真实驱动 demo 系统）。沙箱此前卡死的根因正是缺浏览器，现已解除。
- **风险**：⚠️ 仍建议在 CI 中标注「需浏览器+真实系统」，避免无头环境挂死；或将集成测试改用 `memory` 引擎离线冒烟。

### ✅ 绿包（contracts / infra-* / stage-feature / stage-defect / stage-explore / stage-case / stage-execute）
- 全部 `verify` 通过；`typecheck`/`lint` 在递归跑中除 engine-mcp 外无 `ERR_PNPM` 报错。
- **建议**：仍建议对每个绿包单独跑一次 `typecheck` 确认（递归 typecheck 在 engine-mcp 处 `bail`，后续包未被独立校验）。

## 六、可复现 Bug 明细（出现步骤）

### BUG-1｜`pnpm build` 全库构建失败（engine-mcp）
- **复现步骤**：`cd D:\newTest` → （干净态）`rm -rf packages/*/dist` → `pnpm build`
- **期望**：所有包编译产出 `dist/`
- **实际**：在 `@test-platform/engine-mcp` 失败，`TS2307: Cannot find module '@test-platform/infra-ai'`
- **根因**：构建不保证 `infra-ai` 的 `dist` 先于 `engine-mcp` 生成（`composite:false`，类型经 `dist` 解析，无 project references）。
- **影响**：🔴 阻断生产构建与一键部署。
- **修复方向**：① 加 TypeScript project references（`composite:true` + `references`）；或 ② 构建前按拓扑 build；或 ③ 用 tsconfig `paths` 把 `@test-platform/*` 指向 `src`（与 vitest 对齐，统一两套解析）。

### BUG-2｜stage-login 登录状态错误返回 `barrier`
- **复现步骤**：`pnpm --filter @test-platform/stage-login verify` → 看 `verify/login.verify.ts`（`credential 成功登录`~148 行等）
- **期望**：成功→`ok`，凭据/硬失败→`failed`
- **实际**：上述场景均返回 `barrier`
- **E2E 端到端复现（v2）**：`npx playwright test` 的 `demo-integration › 1. 登录流程`：`POST /api/stage {stage:"login", mode:"no-login"}` **10s 超时无响应**（日志未打印 HTTP 状态，直接 `TimeoutError: apiRequestContext.post: Timeout 10000ms exceeded`）。
- **影响**：🔴 首阶段即错，下游整条流水线拿不到有效会话；且已在真实集成中复现为调用方超时。
- **修复方向**：核对登录状态机在 success / wrong-credential / captcha / hard-fail 各分支的返回值映射；确认 no-login 模式是否应直接返回 `ok` 会话而非进入 `barrier` 等待。

### BUG-3｜app 前端 78 类型错误 + 47 测试失败
- **复现步骤**：`pnpm --filter @test-platform/app typecheck` / `verify`
- **期望**：typecheck 0 错误、verify 全绿
- **实际**：大量 UI 组件编译/渲染不通过（但 **`vite build` 成功、运行时 UI 可渲染**——见 v2 修正）
- **影响**：🔴 前端类型安全与单测覆盖缺失，不可维护级。
- **修复方向**：先消 typecheck（多因 contracts 类型变更未同步到 app 的 `services/pipeline.ts`、`screens/*.tsx`）；再修 failing tests。

### BUG-4｜orchestrator verify 需真实浏览器（原「不可离线」）
- **v2 状态**：**浏览器已装，环境死局解除**。在有浏览器的机器上 `pnpm --filter @test-platform/orchestrator verify` 可跑；E2E `demo-integration` 即对其 `/api/stage` 的端到端验证且已证明引擎能真实驱动 demo 系统。
- **剩余风险**：⚠️ 无头 CI 仍会挂死；建议标注门禁需浏览器，或改用 `memory` 引擎离线冒烟。

### BUG-5（轻微）｜`pnpm madge` 脚本损坏
- **复现**：`pnpm madge` → `ENOENT: packages/*/src`（glob 未展开）
- **修复**：脚本改为 `madge --circular --extensions ts packages/*/src`（在 shell 中展开）或显式列包。

### BUG-6（v2，已解决）｜Playwright/Chromium 浏览器缺失导致 E2E 起不来
- **复现（原）**：`npx playwright test` → `browserType.launch: Executable doesn't exist ... chromium-XXXX/chrome-win/chrome.exe`
- **修复（v2）**：`node node_modules/playwright/cli.js install chromium`（下载 Chrome for Testing 151.0.7922.34 / 191.8 MiB 至默认缓存 `~/.cache/ms-playwright`），launch 验证 `LAUNCH_OK`。
- **影响**：🔴 原阻塞所有真实 E2E；**现已解除**。

### BUG-7（v2，新发现·真实集成）｜功能点「风险/优先级」字段验证超时 + 用例表数据依赖
- **复现**：`npx playwright test` →
  - `core-feature › S3 功能点: 风险和优先级字段验证`（33.2s 超时）
  - `core-case › S4 用例: 表格结构和列完整性`（7.6s，`expect(table).toBeVisible()` 失败）
  - `demo-integration › 3. 功能点生成`（33.3s 超时）、`4. 测试用例生成`（8.8s，table 不可见）
- **分析（v2）**：
  - 用例表（`core-case` 第 1 个 / `demo` 第 4 个）**直接进入「测试用例」屏时表格不可见**，需先经过完整流水线产生数据/连接才渲染——属**数据依赖**，测试应先建立连接与数据再断言。
  - 功能点「风险/优先级」字段 33s 仍未填充，疑似依赖后端数据或 AI 生成，需研发定位字段来源。
- **影响**：⚠️ 流水线中后段（功能点→用例）的真实数据产出不稳定，部分依赖 AI/后端，需确认无 AI key 时的降级行为。
- **修复方向**：① 用例表断言前置「先跑通 explore→feature→case 生成数据」；② 定位风险/优先级字段填充逻辑（是否漏接 stage 输出）。
