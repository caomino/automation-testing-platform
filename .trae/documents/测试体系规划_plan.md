# 自动化测试平台 · 测试计划 v4（完整版）

> **被测对象**：`d:\newTest` 项目（自动化测试平台本身）
> **测试方式**：以 S1-S5 目标系统 + 7 套样例系统为输入，验证本平台的 5 阶段流水线
> **页面测试**：使用 `browser_use` skill 进行浏览器自动化测试
> **Bug 平台**：GitHub Issues（免费、已集成、支持结构化字段）
> **修复工作流**：测完一个模块 → 立即记录问题到 GitHub → 派发对应 Agent → 根因修复 → 复测
> **执行策略**：多 Agent 并行节省时间；仅全流程端到端测试用单模型

---

## 一、背景

### 1.1 被测平台概述

**自动化测试平台**是一个商业级 Web 自动化测试系统：用 Playwright 控制浏览器探索被测 Web 系统 → 生成功能点表（九列）→ 生成测试用例表（八列）→ 执行 → 产出缺陷表。

| 维度 | 说明 |
|------|------|
| 技术栈 | React + Vite + Node 后端 + TypeScript + Playwright MCP |
| 架构 | pnpm monorepo，11 个 package + app UI（10 屏） |
| 核心流水线 | 5 阶段：登录 → 探索 → 功能点审核 → 测试用例 → 执行/缺陷 |
| 隔离铁律 | 每 stage 独立 package，I/O 冻结，zod schema 校验 |
| 金标准 | 《区域影像测试用例.xls》（格式参照基准） |
| 适配目标 | 95%+ 标准 Web 管理系统（jQuery/Vue2/Vue3/React/Angular） |

### 1.2 测试目标

| # | 目标 | 说明 |
|---|------|------|
| T1 | 流水线完整性 | 5 阶段可串通：登录→探索→功能点→用例→执行→缺陷 |
| T2 | 10 屏功能正确性 | 每屏核心功能按文档规格实现 |
| T3 | 输出质量 | 功能点九列 + 用例八列符合金标准模板 |
| T4 | 适配能力 | 正确处理 S1-S5 + 7 套样例不同技术栈 |
| T5 | 安全合规 | S5 人大系统严格只读约束 |
| T6 | Bug 闭环 | 测试→记录→修复→复测 全流程跑通 |

### 1.3 测试方法

| 方法 | 工具 | 说明 |
|------|------|------|
| 页面 UI 测试 | `browser_use` skill | 浏览器自动化验证每个屏的 UI 交互 |
| 功能逻辑测试 | 代码审查 + 手动验证 | 验证各模块功能实现 |
| 输出数据核对 | 手动比对 | 探索结果→功能点→用例的数据质量核对 |
| 表格细节测试 | `browser_use` skill | +/× 按钮、单元格合并、行列操作 |
| 绑定关系测试 | 代码审查 + 手动验证 | 功能点⇄用例绑定链完整性 |
| 全流程端到端 | 单模型完整流程 | 5 阶段串通，一个模型跑完整条链 |
| 并行模块测试 | 多 Agent 并行 | 各模块独立测试，节省时间 |

### 1.4 测试数据核对清单

每个阶段输出必须核对：

| 阶段 | 核对内容 | 核对标准 |
|------|----------|----------|
| 探索 | 模块树是否按系统功能分层 | 覆盖所有菜单，结构正确 |
| 探索 | 每个模块的 DOM 证据是否充分 | 导航类证据齐全，数据类标记 needs_review |
| 功能点 | 功能点是否全面 | 覆盖探索到的每个模块，无遗漏 |
| 功能点 | 九列格式是否正确 | 与金标准模板一致 |
| 功能点 | 测试点标识是否正确 | 3 段 base + NN 递增，唯一不冲突 |
| 用例 | 用例是否覆盖全部场景 | 6 维度：Normal/Exception/Boundary/Process/Permission/Data |
| 用例 | 用例编号与功能点绑定 | 用例编号 = 功能点测试点标识_NN |
| 用例 | 八列格式是否正确 | 与金标准模板一致，列宽正确 |
| 用例 | 场景是否具体可执行 | 步骤明确，无泛化描述 |
| 执行 | 数据隔离是否合规 | 仅操作本任务数据，快照比对通过 |

4. 测试 Agent 继续执行后续步骤
5. 标记该用例为「人工协助」

## 七、修复工作流（即时闭环）

### 7.1 即时工作流

```
步骤 1: 测试 Agent 测完模块 X
  ↓
步骤 2: 立即在 GitHub 创建 Issue（Labels: module:X + severity + system）
  ↓
步骤 3: Assign 给对应 Agent（Agent-A~E）
  ↓
步骤 4: Agent 阅读代码 → 根因分析 → 结构性修复
  ↓
步骤 5: 修复后更新 Issue 状态 → 指派回测试 Agent
  ↓
步骤 6: 测试 Agent 复测 → 通过标记 verified
  ↓
步骤 7: 复测失败 → 重新 assigned 给 Agent 继续修复
```

### 7.2 测试→修复时序（以屏①为例）

| 时间 | 动作 | 执行者 | 产出 |
|------|------|--------|------|
| T0 | 开始测屏① S1 场景 | 测试 Agent | — |
| T0+10min | 发现 BUG-001：阶段进度卡不显示 | 测试 Agent | GitHub Issue #1（label:module:app-ui, severity:P1） |
| T0+11min | Assign BUG-001 → Agent-E | 测试 Agent | Issue assigned |
| T0+30min | 屏①全部测完 | 测试 Agent | Issues #1, #2, #3 已创建 |
| T0+40min | Agent-E 阅读 app/ui 代码 | Agent-E | 完成代码理解 |
| T0+60min | Agent-E 提交修复 PR | Agent-E | PR #x 引用 Issue #1 |
| T0+70min | 测试 Agent 复测 BUG-001 | 测试 Agent | verified → closed |

### 7.3 修复原则

1. **即时记录**：测完一个场景立即建 Issue，不积压
2. **即时派发**：Issue 创建后立即 Assign 给对应 Agent
3. **先熟悉再修复**：Agent 收到 Issue 后先阅读代码理解架构
4. **根因修复**：不打补丁，结构性修复
5. **契约保护**：符合 I/O Boundary，不破坏冻结接口
6. **复测闭环**：修复后立即复测，通过 → verified

### 7.4 测试 Agent 职责

1. 按屏顺序测试（①→②→③→④→⑤→⑥→⑦→⑧→⑨→⑩）
2. 每个屏按场景表逐一执行
3. **每个阶段输出后立即核对数据质量**（见 §1.4 核对清单）
4. 发现问题 → 立即 GitHub Issue（模板 + Labels）
5. 验证绑定关系：功能点测试点标识 ⇄ 用例编号 ⇄ 执行用例
6. 所有场景测完 → 汇总测试报告
7. 接收修复后 → 复测 → 标记 verified
8. 使用 `browser_use` skill 进行页面 UI 自动化测试
9. 表格细节测试：+/× 按钮、单元格合并、行列增删
